## 将棋の終局ルール仕様（KIF-010）

根拠: 日本将棋連盟「対局規則」第2章（制定2024-06-07、改定2024-10-01・2025-01-01・2025-10-01）と連盟FAQ（アマチュア大会の宣言法）。2026-11-15に`www.shogi.or.jp`から原文を確認。

| 規則 | 連盟規則の内容 | 棋友の扱い | 状態 |
| --- | --- | --- | --- |
| 千日手（第8条） | 盤・持ち駒・手番が同一の局面が4回で千日手、先後交代で指し直し | `draw`として記録。先後交代の再戦は今後の画面改善 | 実装済み |
| 連続王手の千日手（第8条8項・第10条10項） | 同一局面4回の一連の手順中、片方の手がすべて王手なら王手側の反則負け | 初回出現から4回目までの手順で判定 | 実装済み |
| 500手（第9条6項） | 合意に至らず500手に達したら持将棋（無勝負・指し直し）。王手中なら連続王手が途切れた時点 | `draw` | 実装済み |
| 入玉宣言法（第9条5項） | 手番で宣言。玉が敵陣3段目以内、敵陣の駒が玉以外10枚以上、王手なし。持ち駒＋敵陣の駒（大駒5点・小駒1点）が31点以上で勝ち、24〜30点で指し直し。1つでも欠ければ宣言側の負け | 既定の規則。`declareEntering`。24〜30点は`draw` | 対局画面とAIに接続済み（ADR-011） |
| 27点法の宣言法（連盟FAQ・アマ大会） | 先手28点以上・後手27点以上で宣言側の勝ち、条件を欠けば負け | 対局設定で選べる。USIエンジンの宣言勝ちもこの系統が多いので、エンジンの判断は必ず`checkDeclaration`で再検証する | 対局画面で選択可（ADR-011） |
| 合意による持将棋（第9条4項） | 両者合意で、全駒の点数（`materialPoints`）が双方24点以上なら指し直し、24点未満の側は負け | 合意の仕組み（AIの受諾判断）が必要なため未実装 | 未実装 |

**採用仕様（ADR-011、2026-11-15ユーザー承認）**
1. 既定は**連盟の現行規則（31点法）**。27点法は対局設定の選択肢として後から追加する。
2. 「入玉宣言」ボタンは自玉が敵陣に入ったときだけ表示する。押すと条件4項目と、その規則での結果（勝ち／引分け／負け）を先に見せてから確定させる。確定後は規則どおり、条件不足なら宣言側の負けとする。教材・練習では負けにしない。
3. AIは結果が「勝ち」になるときだけ宣言する。
4. 引分け（千日手・持将棋・宣言24〜30点）は「指し直し相当」と表示し、先後を入れ替えた再戦を提案する。

## 永続化・プライバシー上の注意

- `/api/progress` は `oai-authenticated-user-id` を主な利用者キーとして使用する。識別にメールアドレスを使わない。
- D1には `games`（結果・USI配列）、`lesson_progress`（完了ID）、`conversations`（発話）がある。現行マイグレーション: `drizzle/0000_early_madame_hydra.sql`。
- GETは対局最大60・チャット最大60を返す。画面はクラウド対局とローカル記録の一部を突き合わせるが、**クラウドの会話を表示状態にマージしていない**。会話の長期記憶を持つという表示は禁止。
- 対局中盤面は主にローカル保存。端末変更・キャッシュ消去・誤同期へのバックアップ保証はまだない。
- D1の本番データはこのGitリポジトリには含めない。DBの本番操作・破壊的移行にはユーザー確認が必要。

## 将来の責務分離（基本方針採用、実装・技術選定は未着手）

1. `rules / notation`：将棋の全合法手・終局・USI/SFEN/KIF/CSA変換と十分な検証。
2. `USI engine adapter`：合法局面を独立した将棋エンジンへ渡し、解析・候補手・スコアを受け取る。プロセス間境界を想定し、プロトコル・時間制限・故障時代替を検証する。
3. `rival policy`：レーティング、棋風、戦型選択、局面依存の「人間らしい」着手生成。エンジン本体と分離。
4. `tutor`：ユーザーの弱点推定、カリキュラム、復習・問題の検証、実戦との連携。
5. `conversation + grounded memory`：LLMの人格応答と、ユーザーの対局事実・許可された長期記憶の参照を分離。
6. `data/API`：後方互換スキーマ、同期、プライバシー、エクスポート・復元。

**採用エンジン・実行場所は決まっていない。** Cloudflare Workers上での重量級探索は実行制約の検証が必要。ブラウザWASM/別サービス/サーバー側などの候補を、計測・ライセンス・費用の証拠とともに比較する。

エンジンプロセスの分離は設計方針だが、**分離によってGPLの義務が自動的に消えると判断しない**。本体ライセンスと評価関数・定跡を別々に調査する。詳細・一次資料・検証手順は [ENGINE_INTEGRATION_PLAN.md](ENGINE_INTEGRATION_PLAN.md)。

## 変更時に守る契約

- 盤面の向き：先手=下、後手=上、9〜1筋と一〜九段の座標、文字の回転を維持。iPhoneの小画面でも指せる。
- 指し手：既存 `Game`, `Move`, `usi` の意味を変更する際は既存データ互換性・変換を検証する。
- 試作サイト：非公開状態を維持し、DBを失わず移行できるまで `kifu-rival.v1` とD1のデータを消さない。
- 正確な局面解説を出せない機能は、未対応であることをUI上でも示す。
