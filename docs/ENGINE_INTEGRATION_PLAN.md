# 将棋エンジン採用とライセンスの設計ゲート

更新: 2026-11-16。**エンジンを「棋友の思考の根拠」に使い、人間らしいライバルの振る舞いは別の層で設計する**方針を採用した（ADR-008）。特定エンジンの採用・課金・ライセンス方式は未決。

## 採用済みの論理的境界（独立試作まで実装、本番接続はこれから）

1. **将棋ルール／記譜層** — 検証済み合法手、終局、局面、USI/SFEN等の変換。現在の `lib/shogi.ts` は不完全であり、エンジンへ不正局面を渡さないようテストする。
2. **USI engine adapter** — 指定局面からエンジン候補手・評価値・読み筋・時間等を取得するインターフェース。プロセス起動・タイムアウト・エラー・資源上限・エンジンバージョンはアダプター内で隔離する。インターフェース自体は外部エンジンなしでもモック可能にする。
3. **Rival policy** — ユーザーの技量、対局状態、棋風、戦型多様性から候補手を選ぶ。**単なるランダム悪手で弱体化しない**。棋力を実測で校正する。
4. **Tutor / conversation** — 棋譜解析結果を根拠として教材・感想戦・会話へ展開。エンジンの形勢値だけで自然言語の正確性を保証しない。

`browser / ChatGPT Sites Worker → engine adapter API → independent USI engine process` は**候補アーキテクチャ**。プロセス分離は保守・性能・境界設計に有利だが、独立したプロセスにしただけでGPL上の結合／配布の判断が自動的に解決するものではない。

## GPLの境界（一般的な注意。法的判断は採用時に再検証）

- GPLプログラムの**単なるサーバー上での実行**と、コピー／バイナリの**第三者への配布**は同じではない。GPLv3は通常、ネットワーク越しに利用させるだけでソース開示を要求するAGPLの条項とは異なる。
- ブラウザへエンジンのWASMを配る、エンジンをアプリ配布物へ組み込む、改変版を配布する場合は、GPLのソース提供・通知や結合した著作物の扱いを個別に検討する。
- USIのようなプロセス間通信で**完全に別プログラムとしてやり取りする設計**を基本案とするが、法的な「別著作物」を保証するものではない。API粒度・コード共有・結合実態を監査する。
- 開発元の評価パラメータ・定跡・学習データ・画像には、本体とは異なるライセンスがあり得る。GitHub Publicだから許可不要、という考え方はしない。
- 棋友のルート `LICENSE` は未選定。GPL部品の利用条件・再配布要否を検討してから、自作コード側の採用ライセンスもユーザーと決める。GPLライセンス文は原文と公式資料を確認する。

一次資料: [GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html)、[GPLv3 本文](https://www.gnu.org/licenses/gpl-3.0.html)、上記の公式エンジンリポジトリ。法的な不確実性が残ればエンジンの本番組込・再配布前に専門家確認を検討する。

### 実行場所ごとのGPL上の論点（一般論。法的結論ではない）

1. **ブラウザ内WASM（Web Worker）**: ユーザー端末へエンジンのバイナリを**配布**する形になる。GPLv3の対応ソース提供・ライセンス表示が必要になる見込み。棋友本体とはUSI文字列を`postMessage`でやり取りする別プログラムとする設計を維持する。オフライン動作・サーバー費用ゼロが利点、端末性能とメモリ（ka系は初期256MB）が欠点。
2. **Cloudflare Worker内WASM**: 端末へは配布しないが、Workerの実行時間・メモリ上限の最新公式値を確認する必要がある。シングルスレッド版のみ。
3. **別サーバーのネイティブプロセス**: 最も強く柔軟だが、常時稼働費用が発生する（課金はユーザー承認事項）。

- リポジトリ外の一時ディレクトリでビルド済みWASMを動かし、同一局面集に対する固定時間（例: 0.5s / 2s）の最善手・評価値・ノード数・メモリを記録する。対象はYaneuraOu系シングルスレッド版とFairy-Stockfish WASM。
- 現行`chooseRivalMove` Lv.4との対局（先後入替え・複数局）で強さの差を記録する。
- iPhone Safariでの初期化時間・メモリ・発熱をユーザーの実機で確認する（実機確認はユーザー協力が必要）。
- 評価関数の原典ライセンス（本家配布記事）を直接確認できるまで、その評価関数を採用候補として確定しない。
- `rival policy`は、エンジンのMultiPV候補（上位N手と評価値差）から棋力・棋風に応じて選ぶ設計を第一案とし、ランダム悪手による弱体化は採らない。

## KIF-020 実測 第1回（Claude, 2026-11-15）

ADR-010の許可に基づき、**リポジトリ外の一時環境**でビルド・実行した。第三者のコード・バイナリ・評価関数はコミットしていない。再現手順と条件は[`tests/engine-bench/README.md`](../tests/engine-bench/README.md)。全66局で**エンジンの不正手は0件**（全手を棋友の`legalMoves`で検証し、終局は棋友の`playMove`で判定）。外部エンジンとの突き合わせでも、棋友のルール実装との食い違いは見つからなかった。

### 評価関数・付属データの権利（調査結果）

- **Fairy-Stockfish 将棋NNUE** `shogi-9ab5e57f31d0.nnue`: 公式配布ページに「2026年以降の日付のネットワークはすべてCC0で公開」と明記されている（このファイルは2026-11-03付）。権利面の障害は最も小さい。ただし159MBで、スマホのブラウザへの配布には不向き。
- **YaneuraOu NNUE系**: 本家の評価関数は支援者向けニュースレターで配布されており、公開ダウンロードは確認できなかった。再配布条件は未確認。フォークの「`nn.bin`はMIT」という記載は、原典（本家の配布記事）で未確認。
- **YaneuraOu 駒得版・Fairy手作り評価**: 評価関数ファイルが不要。本体はどちらもGPLv3。
- エンジンの入玉宣言の既定は27点法系（YaneuraOu `EnteringKingRule`の既定値は`CSARule27`。連盟の31点規則に当たる選択肢はない）。エンジンの`bestmove win`は棋友の`checkDeclaration`で再判定する。

### 採用候補の絞り込み（提案。採用はユーザー判断、`Q-003`・`KIF-024`）

1. **第一候補（端末内で動かす最初の強化）**: ブラウザのWeb Workerで動く、**評価関数ファイル不要のエンジン**。候補は公式WASMがあるFairy-Stockfish（手作り評価）か、自前でWASM化したYaneuraOu駒得版。どちらも現行Lv.4に全勝し、追加ダウンロードは約1〜2MB、サーバー費用ゼロでオフラインでも動く。本体はGPLv3なので、配布物にはライセンス表示と対応ソースの提供を付ける（棋友本体とはUSI文字列だけをやり取りする別プログラムの構成を保つ）。
2. **強い解析が必要な場面（感想戦・教材検証・有段者帯）**: Fairy-Stockfish＋CC0の将棋NNUE。最も強く権利も明快だが、159MB・メモリ約440MBのため、スマホのブラウザ内ではなく、PC・サーバー・事前計算向き。サーバーで動かす場合は費用が発生する（承認事項）。
3. **当面は採用しない**: YaneuraOuのNNUE評価関数（入手経路と再配布条件が不明確）、dlshogi（GPUが前提）、`yaneuraou.wasm`（2021年以降更新なし）。
4. **棋力調整**: 棋友の`rival policy`がMultiPVの候補手と評価値差から選ぶ方式を第一案とする。エンジン内蔵の弱体化（Fairyの`Skill_Level`・`USI_Elo`、YaneuraOuの`DepthLimit`・`NodesLimit`）は比較対象として、人間らしさの評価（KIF-022）で使う。

ADR-010/011の試作範囲で、**自作のUSIアダプターと独立した着手選択層を実装し、実際のWASMで動かした**。アプリの対局相手はまだ従来のLv.4のまま。第三者のコード・WASM・評価関数はリポジトリ外に置き、コミットしたのは自作コード、テスト、合成局面の測定結果、手順書だけである。新規課金、実ユーザー棋譜の外部送信、Siteへの配備は行っていない。

### 実装した境界

- `lib/engine/usi-adapter.ts`: USIの起動・設定・準備完了、固定時間の探索、MultiPV、cp/詰み評価・読み筋の取得。通常の対局は初期局面からの手順を渡し、千日手の履歴を保つ。任意の開始局面では現在のSFENを渡す。
- 候補手と読み筋の**全手を棋友の合法手生成で再検証**する。比較可能な候補は同じ探索深さで揃え、評価値の上限・下限だけが返った行は候補比較に使わない。`bestmove win`は棋友の対局で選択した入玉規則で再判定する。
- 結果には盤面だけでなく棋譜・千日手履歴・入玉規則を結び付ける。別の対局状態へは適用できない。中断・応答の期限超過・Worker異常では、そのWorkerを終了して要求を拒否する。次回は新しいWorkerを起動するため、前回の`bestmove`が新しい要求へ混ざらない。
- `lib/engine/rival-policy.ts`: 強い設定はエンジンの最善手を使う。練習設定は同一深さの候補の評価差に上限を設け、攻め・堅実の特徴と再現可能な種を使って選ぶ。王手中や最善候補だけが大きく優る場面では評価差を許容しない。エンジンが詰み評価した候補を優先し、cp評価の候補がある間は負の詰み評価の候補を選ばない。

評価差70/180cp、棋風への加点、候補数3はいずれも**仮設定**である。段級位・Elo・人間らしさを示す数値ではない。今回の対局比較は「強い設定」で行い、練習設定の強さは未校正である。

## KIF-021/022 対局画面への接続 第4回（Claude, 2026-11-16）

PR #21の試作を基に、**開発版のアプリで強いエンジンと一局を通して指せる**ようにした。正式採用・配布・Siteへの配備はしていない。

### 構成（エンジンと着手選択の分離）

| 層 | ファイル | 役割 |
| --- | --- | --- |
| 配信（開発のみ） | `scripts/vite/engine-dev-plugin.mjs`・`engine-bridge.js` | `KIFU_ENGINE_DIR`（リポジトリ外）のエンジンを`/__kiyu-engine/`で配信し、COOP/COEPを付ける。`vite dev`専用で、本番ビルドでは404 |
| 接続 | `lib/engine/browser-engine.ts` | 配信の有無と分離設定を確かめ（`probeDevEngine`）、1対局相手につき1つのWorkerを作る |
| 1手の手続き | `lib/engine/engine-rival.ts` | 起動→強さに応じた時間で探索→着手選択。中断・期限超過・障害でWorkerを捨て、次の手番で新しく起動 |
| 着手選択 | `lib/engine/rival-policy.ts` | エンジンが探索・検証した候補から選ぶ。**乱数を使わない**（同じ局面・設定なら同じ手と説明） |
| 画面 | `hooks/use-engine-rival.ts`・`app/rival-app.tsx` | 対局相手の設定（対局ごとに固定）、考慮時間の表示、中断・再開、失敗時の再試行と内蔵AIへの明示的な切替、直前の手の理由の表示 |

着手選択層は「わざと悪い手を混ぜる」方式を取らない。強さは(1)エンジンの探索時間と(2)最善候補からの評価差の許容幅で決め、許容幅の中では次の順で選ぶ。

1. 詰みがあれば最短の詰みを指す（本気は最善手そのもの）。
2. 王手を受ける局面や、他の候補が大きく劣る局面では最善手。
3. 「互角を目指す」「練習」で棋友が目標以上に優勢なら、評価が目標の差（+300／+100）に近い候補を選ぶ（**接戦を保つための実力適応**）。劣勢・互角なら許容幅の中の最善候補。
4. 棋風は小さな加点（攻め好き: 駒取り・王手・成り、手堅い: 取られる場所へ出ない）で、許容幅を超えて効くことはない。
5. 目的「勝ち切る練習」では棋友は投了せず、学習者が詰ますまで指し続ける。「本気」は3手以内の詰みを読み切ったら投了する。

| 強さ | 探索時間/手 | 候補数 | 許容幅 | 優勢時の目標 |
| --- | --- | --- | --- | --- |
| 本気 | 1秒 | 3 | 0（最善手） | なし |
| 互角を目指す | 0.5秒 | 5 | 80 | +300 |
| 練習 | 0.3秒 | 5 | 200 | +100 |

すべて仮設定で、段級位・Eloではない。
