# 将棋エンジン採用とライセンスの設計ゲート

更新: 2026-11-15。**エンジンを「棋友の思考の根拠」に使い、人間らしいライバルの振る舞いは別の層で設計する**方針を採用した（ADR-008）。特定エンジンの採用・課金・ライセンス方式は未決。

## 採用済みの論理的境界（実装はこれから）

1. **将棋ルール／記譜層** — 検証済み合法手、終局、局面、USI/SFEN等の変換。現在の `lib/shogi.ts` は不完全であり、エンジンへ不正局面を渡さないようテストする。
2. **USI engine adapter** — 指定局面からエンジン候補手・評価値・読み筋・時間等を取得するインターフェース。プロセス起動・タイムアウト・エラー・資源上限・エンジンバージョンはアダプター内で隔離する。インターフェース自体は外部エンジンなしでもモック可能にする。
3. **Rival policy** — ユーザーの技量、対局状態、棋風、戦型多様性から候補手を選ぶ。**単なるランダム悪手で弱体化しない**。棋力を実測で校正する。
4. **Tutor / conversation** — 棋譜解析結果を根拠として教材・感想戦・会話へ展開。エンジンの形勢値だけで自然言語の正確性を保証しない。

`browser / ChatGPT Sites Worker → engine adapter API → independent USI engine process` は**候補アーキテクチャ**。プロセス分離は保守・性能・境界設計に有利だが、独立したプロセスにしただけでGPL上の結合／配布の判断が自動的に解決するものではない。

## GPLの境界（一般的な注意。法的判断は採用時に再検証）

- GPLプログラムの**単なるサーバー上での実行**と、コピー／バイナリの**第三者への配布**は同じではない。GPLv3は通常、ネットワーク越しに利用させるだけでソース開示を要求するAGPLの条項とは異なる。
- ブラウザへエンジンのWASMを配る、エンジンをアプリ配布物へ組み込む、改変版を配布する場合は、GPLのソース提供・通知や結合した著作物の扱いを個別に検討する。
- USIのようなプロセス間通信で**完全に別プログラムとしてやり取りする設計**を基本案とするが、法的な「別著作物」を保証するものではない。API粒度・コード共有・結合実態を監査する。
- 開発元の評価パラメータ・定跡・学習データ・画像には、本体とは異なるライセンスがあり得る。GitHub Publicだから許可不要、という考え方はしない。
- 棋友のルート `LICENSE` は未選定。GPL部品の利用条件・再配布要否を検討してから、自作コード側の採用ライセンスもユーザーと決める。GPLライセンス文は原文と公式資料を確認する。

一次資料: [GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html)、[GPLv3 本文](https://www.gnu.org/licenses/gpl-3.0.html)、上記の公式エンジンリポジトリ。法的な不確実性が残ればエンジンの本番組込・再配布前に専門家確認を検討する。

### 実行場所ごとのGPL上の論点（一般論。法的結論ではない）

1. **ブラウザ内WASM（Web Worker）**: ユーザー端末へエンジンのバイナリを**配布**する形になる。GPLv3の対応ソース提供・ライセンス表示が必要になる見込み。棋友本体とはUSI文字列を`postMessage`でやり取りする別プログラムとする設計を維持する。オフライン動作・サーバー費用ゼロが利点、端末性能とメモリ（ka系は初期256MB）が欠点。
2. **Cloudflare Worker内WASM**: 端末へは配布しないが、Workerの実行時間・メモリ上限の最新公式値を確認する必要がある。シングルスレッド版のみ。
3. **別サーバーのネイティブプロセス**: 最も強く柔軟だが、常時稼働費用が発生する（課金はユーザー承認事項）。

### 次の実測（KIF-020の残り。採用前の実験であり統合ではない）

- リポジトリ外の一時ディレクトリでビルド済みWASMを動かし、同一局面集に対する固定時間（例: 0.5s / 2s）の最善手・評価値・ノード数・メモリを記録する。対象はYaneuraOu系シングルスレッド版とFairy-Stockfish WASM。
- 現行`chooseRivalMove` Lv.4との対局（先後入替え・複数局）で強さの差を記録する。
- iPhone Safariでの初期化時間・メモリ・発熱をユーザーの実機で確認する（実機確認はユーザー協力が必要）。
- 評価関数の原典ライセンス（本家配布記事）を直接確認できるまで、その評価関数を採用候補として確定しない。
- `rival policy`は、エンジンのMultiPV候補（上位N手と評価値差）から棋力・棋風に応じて選ぶ設計を第一案とし、ランダム悪手による弱体化は採らない。
